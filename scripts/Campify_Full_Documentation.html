Chapter 1: System Overview, Business Context & Vision

1.1 Project Background & Problem Statement

In modern higher education institutions and collaborative youth spaces, students, creators, and developers operate across disconnected digital silos. Traditional social media giants like Instagram, TikTok, and Threads excel at algorithmic viral dopamine loops and high-production visual entertainment, but they lack native tooling for student collaboration, academic networking, project team matching, and micro-learning. Conversely, enterprise platforms such as LinkedIn feel formal, corporate, and detached from the day-to-day creative energy of campus life. Generic collaboration tools (e.g., Discord or Slack) lack cohesive public discovery feeds, dynamic creator portfolios, and structured event registries.

This fragmentation induces acute friction:

  • Hackathon Team Formation Deficit: Students seeking teammates with specific complementary skill sets (e.g., a React Native engineer partnering with an AI researcher and UI/UX Figma designer) must post ad-hoc messages across fragmented WhatsApp groups, Discord channels, or campus bulletin boards.
  • Lack of Real-time Skill Micro-Credentialing: Students lack a casual yet professional social portfolio to showcase GitHub projects, verified technical skills, and hackathon certifications alongside their creative social persona.
  • Superficial Content Overconsumption: Video feeds on existing short-form platforms encourage passive scrolling with negligible educational retention or intellectual challenge.
  • Centralized Community Disconnect: Campus clubs, tech societies, and project teams struggle to broadcast announcements, schedule campus events, host real-time community polls, and moderate abuse from a single centralized hub.

Campify (interchangeably referred to by its campus edition moniker Campify) was engineered specifically to solve these fundamental bottlenecks. By unifying the fluid aesthetics and high-engagement features of modern consumer social networks with purpose-built academic discovery mechanisms, Campify delivers an ecosystem where creative expression seamlessly empowers technical collaboration.

1.3 Key Architectural & Functional Innovations

Campify introduces multiple unique architectural paradigms that elevate it beyond generic social clones:

1. Hybrid Social-Academic Graph

Unlike traditional platforms where a follow relationship merely modifies an algorithmic feed, Campify's social graph directly feeds into its Project Team Matchmaker and Close Friends circuits. The platform calculates affinity scores based on shared campus enrollment, mutual follow graphs, and complementary skill tags (e.g., Python + Figma + Docker).

2. Ephemeral Content Multi-Tier Architecture

Campify implements a comprehensive ephemerality matrix:

  • 24-Hour Stories: Media expiring precisely 86,400 seconds from upload, supporting Close Friends restriction, audio background streaming, and permanent user highlight grouping.
  • Status Notes: Lightweight 60-character status bubbles tethered to user avatars in the direct message workspace, expiring after 24 hours with optional embedded audio snippets.
  • Instants: High-priority ephemeral broadcasts dispatched to specific designated recipient circles, self-destructing post-expiration.

3. Gamified Educational Retention Engine

Traditional educational portals suffer from abysmal retention rates. Campify gamifies micro-learning by embedding 4-choice interactive quizzes directly into short-form educational reels. Submitting a correct answer immediately increments the user's XP score, maintains their continuous daily streak, and positions them on campus leaderboards with Bronze, Silver, Gold, or Diamond tier badges.

2.2 Frontend Framework & Presentation Layer

The Campify presentation tier is structured utilizing modern client-side and server-side rendering paradigms:

  • Next.js 16 (App Router): Implements directory-based routing (src/app/) with unified root layout, dynamic route segment resolution (src/app/[username]), streaming SSR, and optimized asset bundling.
  • React 19 Core: Leverages modern concurrent rendering, granular state synchronization, and reactive effects to deliver instantaneous UI updates without full page reloads.
  • Tailwind CSS v4: Powered by the high-performance @tailwindcss/postcss engine, standardizing design tokens across color palettes (cyan, orange, card slate), custom glassmorphism backdrops, and active-shrink button physics.
  • Zustand 5.0 State Architecture: Lightweight, un-opinionated state management across two global stores:
    • authStore.ts: Maintains current authenticated user credentials, active token headers, persistent login sessions, and logout teardown logic.
    • socketStore.ts: Manages the active Socket.io client instance, online user identity maps, and global presence indicators.
  • TanStack React Query 5.101: Coordinates asynchronous server state caching, background query refetching, and cache invalidation upon post creation or likes.
  • Framer Motion 12.40: Provides physics-based spring animations for collapsible sidebars, floating search drawers, reel swipe physics, and unread notification badge pulses.
  • Lucide React: 100% vector SVG iconography ensuring ultra-crisp display at any viewport density.

2.3 Backend Engineering & Controller Layer

The backend is developed with Node.js v24 and Express.js (TypeScript) adhering to the Controller-Service-Repository structural pattern:

  • Middleware Pipeline: Incoming HTTP requests pass through helmet for secure HTTP header injection, cors for origin validation, and express-rate-limit to deter automated brute-force attempts on sensitive endpoints.
  • Authentication Guard: The authenticate middleware parses Bearer JWT access tokens, validates HMAC SHA-256 signatures, extracts user payload claims, and decorates the Express Request object.
  • Role-Based Access Control (RBAC): The authorize(['ADMIN', 'MODERATOR']) guard verifies user privilege level before permitting execution of administrative or moderation triage controllers.
  • Controller Modularity: Business logic is organized into 19 dedicated controller modules: auth, user, post, reel, story, chat, notification, moderation, admin, ai, community, event, skills, team, learning, gamification, note, instant, and upload.

2.4 Database Engine & Persistence Layer

Campify utilizes Prisma ORM 5.10.2 as its type-safe database abstraction engine:

  • Zero Schema Drift: All database models, constraints, unique keys, and relations are declared in backend/prisma/schema.prisma and compiled into strongly-typed TypeScript definitions.
  • Relational Cascade Deletions: Foreign key definitions enforce strict onDelete: Cascade rules (e.g., deleting a User automatically cascades to delete their associated profile, posts, comments, stories, and chat memberships).
  • Dual-Engine Compatibility: The Prisma schema supports SQLite (file:./campify.db) for instant zero-dependency local developer execution, and seamlessly connects to production PostgreSQL instances with simple environment variable reconfiguration.

2.5 Real-Time Communication Layer (Socket.io)

The real-time layer is powered by Socket.io 4.7.4 running atop the HTTP server instance:

  • WebSocket Protocol Negotiation: Socket.io establishes bidirectional WebSocket transport with HTTP long-polling fallback for constrained firewall environments.
  • Room-Based Partitioning: Chat messages are broadcast exclusively to subscribed room channels (chat_{chatId}), ensuring message privacy and minimal CPU overhead.
  • Online Presence Tracking: An in-memory Map<string, string> associates active Socket IDs with User IDs, enabling real-time online status indicators across the platform.

2.6 External Cloud & AI Services

  • Google Gemini 2.5 Flash: Communicates via REST endpoint generativelanguage.googleapis.com to provide zero-latency text generation for captions, hashtags, and team skill matching. Includes robust heuristic fallback generators.
  • Cloudinary v2 CDN: Handles high-resolution image uploads, automated WebP compression, aspect ratio cropping, and CDN media distribution.
  • Nodemailer 6.9: Dispatches HTML-formatted 6-digit OTP verification codes and password reset links via standard SMTP transport.

2.7 Cryptographic Subsystem & Security

  • Password Hashing: Utilizes bcryptjs with an adaptive work factor of 10 salt rounds.
  • Dual-Token Lifecycle: Short-lived Access Tokens (15-minute expiration) paired with cryptographically random Refresh Tokens (7-day validity).
  • OTP Rate Limiting: Enforces a maximum of 5 OTP dispatch requests per 10 minutes per IP address to eliminate email spamming and SMS bombing vectors.

3.1 Functional Requirements Matrix (FR-01 to FR-45)

Functional requirements specify the direct behavioral outputs and services the system must execute in response to user stimuli. Requirements are categorized by operational subsystem:

Subsystem 1: Authentication, OTP & Identity Management

Req ID Requirement Title Priority Detailed Functional Specification
FR-01 User Registration CRITICAL The system shall allow new users to register by submitting email, unique username, and password. The system must validate password complexity (minimum 8 characters, alphanumeric + symbol) and hash passwords using bcryptjs with 10 salt rounds prior to persistence.
FR-02 Email OTP Dispatch CRITICAL Upon successful registration, the system shall generate a secure 6-digit numerical One-Time Password (OTP) with an expiration timestamp of 10 minutes and dispatch it to the registered email address via Nodemailer SMTP.
FR-03 OTP Verification CRITICAL The system shall verify submitted OTP codes. Upon successful match, the user account status must transition to emailVerified: true and issue initial JWT session tokens. Submitting an expired or incorrect code must return a 400 Bad Request error.
FR-04 Stateless Login CRITICAL The system shall authenticate users via username/email and password, returning an access token (valid for 15 minutes) and setting an HTTP-only refresh token (valid for 7 days). Banned accounts (status: BANNED) must be rejected with 403 Forbidden.
FR-05 Token Rotation HIGH The system shall provide an endpoint (/api/auth/refresh) allowing client applications to exchange a valid refresh token for a newly generated access token without requiring re-authentication.
FR-06 Password Recovery HIGH The system shall provide self-service password reset flows: users submit their email to receive a signed cryptographic reset token, allowing password modification without knowledge of the existing password.

3.5 Algorithmic Specification: Daily Streak State Machine

Streak Continuation & Reset Window

A streak increments when qualifying activity occurs within the active calendar window. Let deltaHours = (currentTime - lastActiveDate) / 3600000:

  • Condition A (Same Day Activity): deltaHours < 20: Activity is recorded in StreakHistory; streak counter remains unchanged.
  • Condition B (Consecutive Day Activity): 20 <= deltaHours <= 48: Streak counter increments by 1 (dailyStreak = dailyStreak + 1); lastActiveDate updates to now().
  • Condition C (Streak Broken): deltaHours > 48:
    • If streakFrozen === true: Streak is preserved; streakFrozen resets to false.
    • If streakFrozen === false: Streak resets to 1 (dailyStreak = 1).

Chapter 9: Security, Privacy, Moderation & Compliance Engineering

The Campify platform adheres to enterprise defense-in-depth security principles. This chapter details the cryptographic foundation, automated content toxicity scanner, role-based access control (RBAC), and compliance mitigations safeguarding user privacy.

9.1 Authentication Architecture & Cryptographic Token Lifecycle

Campify prevents token theft and session hijacking via a dual-token cryptographic rotation lifecycle:

1. Access Token (Short-Lived)

  • Algorithm: HMAC SHA-256 (HS256) with a 256-bit entropy secret key.
  • Expiration: 15 minutes (900 seconds) from issue.
  • Storage: Stored strictly in client memory (Zustand state store); never persisted in insecure localStorage.
  • Transmission: Dispatched via Authorization: Bearer <token> request header.

2. Refresh Token (Long-Lived)

  • Algorithm: Cryptographically random 64-byte hex string.
  • Expiration: 7 days (604,800 seconds).
  • Storage: Encapsulated inside an HttpOnly, SameSite=Strict, Secure browser cookie.
  • Rotation: Single-use rotation; redeeming a refresh token invalidates the previous token.

9.2 Automated Toxicity Moderation Engine

To maintain safe campus discourse, Campify incorporates an automated heuristic content filter (backend/src/services/moderation.service.ts) that intercepts incoming text before database persistence: 

// Automated Toxicity Scanner Implementation
const TOXIC_PATTERNS = [
  /\b(hate|slur|kill|abuse|threat)\b/i,
  /\b(doxx|swat|raid)\b/i
];

export function scanContentToxicity(text: string): { isClean: boolean; flaggedWords: string[] } {
  const flaggedWords: string[] = [];
  for (const pattern of TOXIC_PATTERNS) {
    const match = text.match(pattern);
    if (match) {
      flaggedWords.push(match[0]);
    }
  }
  return {
    isClean: flaggedWords.length === 0,
    flaggedWords
  };
}

When text triggers the scanner:

  • The post or comment submission is flagged with quarantine: true.
  • An automated Report entity is dispatched into the PENDING triage queue in the Administrator Dashboard.
  • If severe physical threats are detected, the author's account status transitions to temporary mute.

12.3 Real-Time WebSocket Gateway Service (backend/src/services/socket.service.ts)

Manages client connections, presence mappings, room subscriptions, and typing broadcasts: 

import { Server as HttpServer } from 'http';
import { Server, Socket } from 'socket.io';

let io: Server | null = null;
const userSocketMap = new Map<string, string>(); // userId -> socketId
const typingUsers = new Map<string, Set<string>>(); // chatId -> set of userIds

export function initSocketServer(server: HttpServer): Server {
  io = new Server(server, {
    cors: {
      origin: process.env.FRONTEND_URL || 'http://localhost:3000',
      methods: ['GET', 'POST'],
      credentials: true,
    },
  });

  io.on('connection', (socket: Socket) => {
    const userId = socket.handshake.query.userId as string;

    if (userId && userId !== 'undefined') {
      userSocketMap.set(userId, socket.id);
      socket.broadcast.emit('user_online', { userId });
      console.log(`User connected: ${userId} (${socket.id})`);
    }

    // Joining room for specific chats (especially for group chats)
    socket.on('join_chat', ({ chatId }) => {
      socket.join(chatId);
      console.log(`Socket ${socket.id} joined chat room: ${chatId}`);
    });

    socket.on('leave_chat', ({ chatId }) => {
      socket.leave(chatId);
      console.log(`Socket ${socket.id} left chat room: ${chatId}`);
    });

    // Real-time typing indicators
    socket.on('typing_start', ({ chatId, userId: typistId }) => {
      if (!typingUsers.has(chatId)) {
        typingUsers.set(chatId, new Set());
      }
      typingUsers.get(chatId)?.add(typistId);
      
      socket.to(chatId).emit('typing_status', {
        chatId,
        typingUserIds: Array.from(typingUsers.get(chatId) || []),
      });
    });

    socket.on('typing_stop', ({ chatId, userId: typistId }) => {
      typingUsers.get(chatId)?.delete(typistId);
      socket.to(chatId).emit('typing_status', {
        chatId,
        typingUserIds: Array.from(typingUsers.get(chatId) || []),
      });
    });

    socket.on('disconnect', () => {
      if (userId) {
        userSocketMap.delete(userId);
        socket.broadcast.emit('user_offline', { userId });
        console.log(`User disconnected: ${userId} (${socket.id})`);

        // Clean up typing lists
        for (const [chatId, users] of typingUsers.entries()) {
          if (users.has(userId)) {
            users.delete(userId);
            io?.to(chatId).emit('typing_status', {
              chatId,
              typingUserIds: Array.from(users),
            });
          }
        }
      }
    });
  });

  return io;
}

export function getSocketServer(): Server | null {
  return io;
}

export function isUserOnline(userId: string): boolean {
  return userSocketMap.has(userId);
}

export function getOnlineUsers(): string[] {
  return Array.from(userSocketMap.keys());
}

export function sendRealtimeMessage(chatId: string, message: any): void {
  if (io) {
    io.to(chatId).emit('new_message', message);
  }
}

export function sendRealtimeNotification(receiverId: string, notification: any): void {
  const socketId = userSocketMap.get(receiverId);
  if (io && socketId) {
    io.to(socketId).emit('new_notification', notification);
  }
}

export function broadcastUserStatus(userId: string, status: 'online' | 'offline'): void {
  if (io) {
    io.emit(status === 'online' ? 'user_online' : 'user_offline', { userId });
  }
}

export function sendRealtimeMessageDelete(chatId: string, messageId: string): void {
  if (io) {
    io.to(chatId).emit('message_deleted', { chatId, messageId });
  }
}

// Helper to query Gemini API or return smart fallback content
async function queryGemini(prompt: string, fallbackResponse: string): Promise<string> {
  if (!GEMINI_API_KEY || GEMINI_API_KEY === 'mock') {
    return fallbackResponse;
  }

  try {
    const url = `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent?key=${GEMINI_API_KEY}`;
    const response = await fetch(url, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
      },
      body: JSON.stringify({
        contents: [{ parts: [{ text: prompt }] }],
      }),
    });

    if (response.ok) {
      const data: any = await response.json();
      const contentText = data?.candidates?.[0]?.content?.parts?.[0]?.text;
      if (contentText) {
        return contentText.trim();
      }
    }
    return fallbackResponse;
  } catch (error) {
    console.error('Gemini API call failed:', error);
    return fallbackResponse;
  }
}

export async function matchTeamMembers(req: Request, res: Response) {
  try {
    const userId = req.user?.id;
    const { projectTitle, requiredSkills, description } = req.body;

    if (!projectTitle || !requiredSkills || !Array.isArray(requiredSkills)) {
      return res.status(400).json({ error: 'projectTitle and requiredSkills array are required' });
    }

    // Query candidate users from database who possess overlapping skills
    const candidates = await prisma.user.findMany({
      where: {
        id: { not: userId },
        skills: {
          some: {
            name: { in: requiredSkills },
          },
        },
      },
      include: {
        profile: true,
        skills: true,
        badges: true,
      },
      take: 6,
    });

    const prompt = `Given a project titled "${projectTitle}" with requirements: "${description || ''}" needing skills: ${requiredSkills.join(', ')}. Recommend matches from students with skills. Output a brief 2-sentence match summary.`;

    const matchAnalysis = await queryGemini(
      prompt,
      `Identified ${candidates.length} top candidates on campus matching your required skill profile for ${projectTitle}. High synergy for full-stack and design integration.`
    );

    const matches = candidates.map((c) => {
      const userSkillNames = c.skills.map((s) => s.name);
      const matchScore = Math.min(
        100,
        Math.round((userSkillNames.filter((s) => requiredSkills.includes(s)).length / requiredSkills.length) * 100) || 75
      );

      return {
        id: c.id,
        username: c.username,
        name: c.name || c.username,
        avatarUrl: c.profile?.avatarUrl,
        bio: c.profile?.bio,
        skills: c.skills.map((s) => s.name),
        matchScore,
        synergyBadge: matchScore > 80 ? 'Top Match' : 'Great Synergy',
      };
    });

    return res.status(200).json({
      summary: matchAnalysis,
      matches,
    });
  } catch (error) {
    console.error('AI Team matching error:', error);
    return res.status(500).json({ error: 'Failed to run AI team match' });
  }
}
